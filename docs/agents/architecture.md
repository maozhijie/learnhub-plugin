# 架构与门：面向 agent 的章程

本仓库的架构约定不只是注释和 ADR——**它们会失败**：分层规则（R1–R7）、架构门（G1–G9）、命令注册表八道门、类型门与各类棘轮，全部随 `npm test` 全量执行。这篇是它们的地图；每道门的阈值来源与实测链的唯一登记处在 [`tests/README.md`](../../tests/README.md)（门册），裁决与理由在 `docs/adr/`。

## 1. `npm test` 的真实构成

`npm test` = **`npm run typecheck` 先串行跑**（= `node scripts/arch-baseline.mjs --types` 类型门对照 + `node scripts/scan-ui-types.mjs` UI 类型门），然后才是全部测试。

**`npm run build` + `npm run check` 通过 ≠ 运行时安全**：esbuild 只剥类型、不查未定义全局，`node --check` 只验语法。实测教训（#152）：宿主抽离漏了 14 个标识符时，707 个测试全绿、build 通过——只有运行时才会炸。所以 G2 的动态 import 加载冒烟**不可退役**，tsc 看不见模块级初始化路径。

## 2. 棘轮的刚性

类型门、文件规模、窄面宽度等受控量走**精确匹配棘轮**：实测 == 基线——**涨了失败；降了但没同步下调基线也失败（过期即失败）**。两个直接后果：

- 遇到「基线不匹配」的失败**不是 bug，是门在执法**。不要绕过它，先读下面印出的违规行。
- 「我把错误改少了怎么反而失败」是正常现象：修好了就同一次提交里把基线一并下调。看当前实测与违规：`node scripts/arch-baseline.mjs`。按实测重写基线：`node scripts/arch-baseline.mjs --update`——**只在产生这次变更的提交里用**；涨了先看这行长在哪、能不能不长，确实该长（有登记的行为变更/新功能）才同步基线。

## 3. 门红了先裁决：改源码还是修门

门失败只有两种诚实解释：**源码真违规**（改源码）或**门误判**（修门）。裁决办法：读门的判据本体（`scripts/` 扫描器与其自检），拿失败样本问一句「这个失败在说真话吗」。**禁止第三条路**——门不动，只为红变绿去扭曲源码（改签名、换写法、弃能力）：那等于把门的缺陷固化进业务代码，下一个撞门的人还得再绕一次，门的误报面原样保留。实测教训（G1，2026-09-13）：扫描器形参正则不认可选形参 `name?`，函数体内对它的裸调用被误报为未定义标识符，调用方曾为绕门放弃更简洁的直传回调签名；正确动作是修正则、按 §5 铁律①给门补正反两向自检（误报样本不再报、真违规样本仍拦截），并把源码恢复成本来的样子。

## 5. 加新门／改阈值的纪律

- **每个门必须带自检**：构造必然违规的样本、断言门会失败；收集器类门另须断言它能看见目标形态。血的来源：R3 曾因收集器只收相对说明符而**恒过**；G3 的第三方向（门面接线）落地前脚本退出 0，对 30 条多余接线完全不可见。**恒过的门比没有门更坏。**
- **阈值必须是实测数字**，来源写进 ADR 与票面；不拍脑袋写「应该 ≤ N」。
- **与顶层重划冲突的门**：记 ADR 并标注「重划后重推」，不就地改阈值（600/900/12/20/10 这类目标值因此只是记录，不是活动阈值）。

## 6. 分层与顶层不变量（一句话版）

四层：`ui/` → 宿主（`src/index.ts` + `src/host/`）→ engine 门面（`src/engine/index.ts`）→ 子系统。方向规则见 R1–R7；顶层不变量：**只有教练层 `proposals.ts` 能调用图写原语**（`GraphStore.writeRegionDoc`，白名单唯一成员）。裁决见 ADR-0042（分层与规则执法）、ADR-0044（顶层分层与不变量）、ADR-0049（门面终态）。

## 7. 「公共面零改动」的正确读法


这是**逐刀纪律，不是永久不变量**（ADR-0049 更正）：每一刀重构不改公共面，使提交可独立回滚——但产品演化可以有意变更它。真正不可碰的面是**产品契约**：路由路径与响应形状、工具名与 schema、磁盘格式。要动它们 = **行为变更**，必须：票面逐条登记 → 探针快照/基线**同提交迁移**（快照是「变更前 vs 变更后」的唯一证据，`tests/helpers/regen-fixtures.mts` 重录、diff 逐条人审、status 漂移零容忍）→ ADR 登记（参见 ADR-0045 §#185 与 ADR-0047 §修订的先例）。

## 8. 提示词变更纪律（#220 / ADR-0072）

**改模板 = 改生产行为**：模板文本与拼装方式决定模型看到什么，进而决定产出。生成质量两轴（格式契约稳定 / 内容质量）的最上游杠杆就在这里，所以模板变更走**登记 + 过门**两步，不停留在「提交信息里写一句」。

**登记**（**纪律面**：凡是让**最终 prompt 变化**的改动都算——模板文本没动、拼装侧重排、注入面增删也算）：同提交补 `PROMPT_CHANGELOG` 条目（`src/engine/output-contracts.ts`，键 = `PROMPT_KINDS` 键），四件套 `version` / `date` / `changeType` / **`expectedDelta`（预期输出增量）**——「这次改动预期模型输出发生什么变化」。同一版本号下允许第二条登记：模板文本没动但最终 prompt 变了，记在同一版本号下并写明变更面，不冒充版本 bump（先例见 ADR-0065 §6 的 §5 复活登记）。

两道门执法，判据不同、都要绿：

- **提交级**：`npm run prompt-bump -- check`（`scripts/prompt-bump.mts`）——模板版本 bump 的提交必须**同提交**补登记条目（走 git 历史；纪律起点动态发现 = `PROMPT_CHANGELOG` 首次出现的提交，不写死 sha）。测试面 `tests/prompt-changelog.test.ts`：真历史必须绿 + 临时仓库造「bump 不补登记」必须红（两态都是验收原文）。**模板面是清单不是单文件**（`TEMPLATE_FILES`，含历史路径 `src/engine/content.ts`）：判据是版本号**集合差**，面里只留当前路径会把一次纯搬迁读成十几个「首次出现」的新版本号，进而逼人补假增量（#237 / ADR-0075 §3）。
- **状态级**：`tests/output-contract.test.ts::runChangelogGate`——每个模板键的最高登记版本 == 模板头 `<!-- learnhub:prompt/vN -->`、键集合 == `PROMPT_KINDS` 全集。

两者互补：状态级管**完备性**（键覆盖、版本对齐），提交级管**时序**（bump 当次就带登记）。都带 ADR-0047 自检。

**两门都看不见的一类（已知边界，如实登记，别当成门能拦住的形态）**：**同版本号下的 prompt 变化**——改模板文本而不 bump、改拼装缝（`prompt-assembly.ts`）、注入面增删。提交级门的判据是**版本号集合差**、状态级门的判据是**版本号对齐**，两者都只看版本号，这类变更两门都不红。它靠**人审 + 上面的登记纪律**兜（登记面是同一版本号下的第二条/第三条条目，先例见 ADR-0065 §6、ADR-0071 §后续）；要把它机械化需要「哪些键的模板文本变了」的键级判据（解析 `PROMPT_KINDS` 模板字面量），代价与脆性都高，本票不做（ADR-0072 §已知边界 ③）。

**过门**（改模板当次必跑）：两条机械读数，都绿才落地。

1. **语料回放**：`npm run prompt-bump -- replay --corpus <语料目录>`——把生成语料（#213）里存下来的真实输出重新过一遍本站解析面，**基线通过 → 回放失败**即回归（解析容忍被改坏的机器判据）。零样本按失败处理（空语料回放会恒过）。
2. **评审对照**：`npm run prompt-bump -- compare <改前.json> <改后.json>`——**同源样本**上逐（站 × 维度）均值不降；两份报告来自 `npm run quality-review -- --out <json>`（改前 / 改后各一次）。同源样本、维度集合一致、非零样本是硬前提，不满足即**拒绝比对**（不是通过）。

**取不到就不假装**：真实语料目录或真模型报告取不到时，如实登记「未过门」与理由（含回退点），不得以「改动很小」为由跳过——ADR-0065 §6 的 §5 复活就是这种「未做真模型对照即落地」的登记先例。分层法庭仍然适用：本装置只出「回放没坏、评分没降」的机械读数，内容质量是否变好归人审（ADR-0070）。
