# ADR-0066: 修复轮策略单源——机制登记与实现对账；出题整批修复轮维持不设

日期：2026-09-13 ｜ 票：#217 ｜ 总纲：#212（生成管线稳定性与内容质量工作流）｜ 前置：#214（契约注册表）

## 背景与问题

#212 §二的事故共性：**全部生成事故都是契约矛盾/边界不清，零例是 YAML 语法错、零例是解析器 bug**。修复模式（裁剪包→容忍解析→回灌修复轮→稳定码）已经体系化，但每站的修复策略散在提交信息、ADR 散文与各站实现里，没有集中登记处——#214 落了注册表 `repair` 列（如实登记现状：罗盘 0 轮＝金样本锚定、回执 0 轮＝ADR-0004 事务性、出题无整批轮），但那一列当时只是**散文**：改了实现没人提醒登记失真，登记失真也没人提醒实现越界。

## 裁决

### 1. 修复策略单源 = 注册表 `repair` 列 + 机制登记表（`REPAIR_MECHANISMS`）

每条策略必须点名**持有该回路的机制**（只许取登记表的键）：

- `mechanism`：持有 `rounds` 轮回路的机制；**`(rounds === 0) === (mechanism === 'none')`**——「0 轮＝无整批修复轮」从注释里的一句话变成会失败的不变式。
- `perItem`：**不属于「几轮」范畴**的逐题/逐项回路（出题站的两个「恰一次」从此有名字：`invokesOncePerQuestion`、`auditRepairOncePerQuestion`，不再只活在 `feedback` 散文里）。

机制登记表每行给 `file`（实现文件）+ `witness`（该文件里真实存在的稳定串，多见证串用于逐级阶梯——节正文的三根横档缺一不可）+ `what`。门（`tests/repair-policy.test.ts`）拿登记与 src/ 对账：**登记一个不存在的回路、或回路改名/删除后登记没跟上，都红。**

逐站核过一遍实现与登记（#217 验收的第一项），**抓出一处登记失真**，其余相符：

| 站 | rounds | mechanism | 实测依据 |
|---|---|---|---|
| 课程大纲 | 1 | `outlineRepairFeedback` | `generation-jobs.ts`：可修死因（OUTLINE_BUDGET/OUTLINE_SHAPE/MODEL_YAML）回灌，其余原样上抛；行为锁 = 调用数 == 1 + rounds（`host-runtime.test.ts`） |
| **课程节拆分** | **0**（原登记 1，失真） | **`none`** | 实现对 `splitOverflowSection` **只发一次调用**，解析失败原样上抛、由管线记入该节失败清单——`outlineRepairFeedback` 的唯一调用点在大纲轮（`jobs.ts:852`）。旧散文声称「同大纲站的死因回灌」是把「同款解析容忍」误读成「同款修复轮」。**登记按实现改**（不是反过来）：拆节是节正文修复阶梯的末级，它自己不再有下一级。行为锁 = 调用数 == 1 + rounds（`host-runtime.test.ts`，本次新增） |
| 课程节生成（正文/交互件） | 2 | `sectionRepairLadder` | `host/jobs.ts`：块级局部修补 → 整节压缩（deep 升档）→ 溢出交拆节 |
| 种子起草 | 1 | `seedRepairPrompt` | 干跑门未过回灌重出完整 YAML 恰一次 |
| 目标反编译 | 1 | `decompileRepairPrompt` | 双产物/名字对账死因回灌恰一次 |
| 教练生长 | 1 | `gateRepairRound` | 受理门反馈 + 被拒裁决回灌重裁（repair 单发） |
| 里程碑草案 | 1 | `milestoneStructureRepair` | 轻量结构门回灌（gateRepairRound 复用） |
| 判卷 / 申诉判卷 | 1 | `gradingReaskOnce` / `disputeReaskOnce` | 解析失败自动重问一次，仍败零落盘 |
| **罗盘** | **0** | `none` | 路线门首过即落盘（金样本锚定），调用数恒 1 在 `tests/compass.test.ts` 锚定 |
| **回执评审** | **0** | `none` | ADR-0004 事务性：解析失败回执与 EMA 零落盘 |
| **题目生成 / 笔记出题** | **0** | `none`（perItem 两枚） | 无整批修复轮；逐题补标与非一致题修复是逐题回路 |
| 独立解题 / 错误对比卡 / 计划草案 | 0 | `none` | 失败即断或零落盘，无回路 |

**覆盖边界（不假装已全覆盖）**：机制登记只证明「这条回路存在」；「本站的 `mechanism` 字段指的就是它」靠两样东西——`REPAIR_ROUND_LOCKS` 的行为锁（站 → 断言调用数的测试文件；`null` = **显式登记的缺口**，还没数过调用数）与逐站人工审查。门强制：rounds > 0 的站必须在锁表内（有锁或显式缺口，漏登即红）、有锁的站其测试文件必须存在。缺口现在看得见，而不是不存在。

### 2. 行为侧锁「几轮」（不是只锁登记文本）

`tests/repair-policy.test.ts` 用脚本化模型 + 必败产物数模型调用次数：

- **出题站 0 轮**：产出不可解析 → **恰一次调用即断**；逐题门全部拒收 → 仍是恰一次调用、零落盘 fail loud。
- **回执站 0 轮**：评审不可解析 → 恰一次调用即断（ADR-0004）。
- **大纲站 1 轮**：调用数 == `1 + 注册表 rounds`（`tests/host-runtime.test.ts` 的 MODEL_YAML 回灌用例）——注册表写 2 就红，实现偷偷多跑一轮也红。
- **拆节站 0 轮**：拆分产物不可解析 → 恰一次拆节调用、无回灌重产（`tests/host-runtime.test.ts`，本次新增；正是「登记失真以行为锁收口」的样板）。
- **罗盘 0 轮**：恒 1 调用由 `tests/compass.test.ts` 的金样本回放闸承载。

站 → 锁的对照表是数据（`REPAIR_ROUND_LOCKS`），门强制它覆盖所有 rounds > 0 的站；`null` 是**显式缺口**（目标反编译/教练生长/里程碑草案/判卷/申诉判卷/课程节生成 目前为 `null`）。

### 2b. 这一轮的复核抓出的两处失真（都按实现改登记）

1. **课程节拆分**：旧登记 `rounds: 1 + outlineRepairFeedback` 与实现对不上（见 §1 表）。改登记为 `0 / none` 并补行为锁——**这正是 #217 存在意义的实例**：散文登记漂移不会自己暴露，得有人去读实现。
2. **机制登记的覆盖边界**：门只能证明「回路存在」，不能证明「本站指的就是它」。这条边界写进 §1 与门注释，并由 `REPAIR_ROUND_LOCKS` 把未锁的站显式列出来（此前它们既没锁也没标记，读起来像已覆盖）。

### 3. 出题整批修复轮：**维持不设**（预注册触发条件）

票面要求「逐题门拒收原因（转义/答案形态/invokes 不在册/查重）回灌、只重出被拒题——参照 outlineRepairFeedback / gateRepairRound 族；成本收益**给数据后**在票内裁决」。裁决为**暂不设**，理由逐条：

1. **数据面缺席**：判断依据是「被拒题的回复率与收益」，而本仓当前零真模型语料（`state/生成语料` 空、`tests/fixtures/` 只有题库与多样性基线快照）。语料回放（#213）能复算的是既有样本的门通过情况，不能凭空给出「加一轮能救回多少」。**举证责任在改动方**：在没有证据说收益为正的前提下加一轮重产，是在推理最重的站上确定性地翻倍成本。
2. **「恰一回灌」族的前提不成立**：族内成员（大纲/种子/反编译/里程碑）共同的形态是**一个便宜的确定性门 + 一个稳定失败码**（MODEL_YAML / OUTLINE_SHAPE / SEED_GATE_FAILED），死因可回灌且模型能据此自我修正。出题站的逐题拒收是**异质集合**：转义损坏已有确定性修复（`repairQuestionStrings`，修不好才拒收）；答案形态是 schema 口误；`invokes 不在册` 已由 `invokesOncePerQuestion` 覆盖（恰一次）；**查重命中不是「修一下」能解决的**——它要求换考点或换问法，正是最容易再次撞查重的那一类。把四种死因混成一锅回灌，回灌文本对其中至少一半没有可执行指令。
3. **判卷轴已经有逐题回路**：#223 的第二意见门对不一致题做恰一次回灌修复并原位替换（`auditRepairOncePerQuestion`，deep 档）——「模型自己错了答案键」这一类最有价值的修复已经存在，且比整批回灌更精准。
4. **更便宜的杠杆已在本轮落地**：#218 的契约后置与 few-shot（大纲/出题各一个完整示例）直接打在**格式稳定**这个上游成因上；先看这两个杠杆的读数，再谈要不要在末端加一轮重产。

**预注册触发条件**（满足任一即重开评估，届时按本 ADR 的 §1 形态接入 `perItem`）：

- #213 语料里出题站的逐题拒收率 **≥15%**（分母 = 模型产出的题数），且其中 ≥1/3 的死因属「改一下就好」类（答案形态 / 记谱口误）——这时回灌文本对多数死因可执行；
- 或 #222 评审器发现「被拒题对应的考点在题库里长期缺题」——即拒收造成了真实的覆盖缺口。

数据来源已就位：`questionGenerate` 的返回值与任务消息带 `rejected[]`（逐题死因原文）、`duplicates[]` 与多样性三读数（#230），语料（#213）落每次调用的渲染提示词与原始输出——拒收率与死因分布可从这两处复算，不需要新建测量面。

### 4. 死因码人话化（票面验收的条件项）

「死因码人话化照 MODEL_YAML 先例」是**若加修复轮**才生效的条款；本轮裁决为不加，故不适用。既有的人话化面（`MODEL_YAML` 的中文语境前缀、`OUTLINE_SHAPE`、`SEED_GATE_FAILED`）保持原样，未做无谓扩张。

## 后果

- 修复策略从「散落散文」变成「登记 + 门执法」：改实现忘了改登记会红，改登记编造回路也会红。
- 出题站的 0 轮是一个**有理由、有触发条件**的裁决，不再是「还没做」——`rejected[]` 报告面与预注册阈值让下一次评估有明确起点。
- 代价：新增机制时要同时登记 `file` + `witness`；见证串随重构改名会让门红——这是有意的同步成本（与 ADR-0061 的代价同源）。
