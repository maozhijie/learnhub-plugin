# 门面终态：hub 降级为容器，公开面改子系统路径

门面 `LearnhubEngine` 今天 **1803 行 / 222 个方法**，其中 **199 个是纯转发**（方法体恰好一条 `return/await/yield* this.<子系统>.<m>(...)`），占 **700 物理行**；非转发只有 23 个（构造 168 行、`errorExplainPack` 42、`questionAudit` 35 等）。ADR-0043 把拆分定为「聚合+转发」并让门面保留全部公共方法做一行转发；ADR-0045 把「**门面转发层消失或自动生成**（消费方直连子系统）」列为终极形态、**另开票，本 ADR 不裁**。本 ADR 就是裁那件事：定终态为 **C 形态**——hub 保留但**降级为纯容器**，公开面从扁平方法名改为 `engine.<子系统>.<方法>`，**199 个转发体删除**。**本 ADR 只定终态，不施工**（施工见 #182，立而不排期）。

理由：ADR-0043 的裁决**没有错，但它定的是过渡形态**。它的理由原文是「门面的价值是公共面的稳定（host/UI/tests 都只认它），病灶只是方法体堆积」与「聚合+转发让拆分成为纯机械搬移——**签名不动、调用点不动、每刀可独立回滚**」——它的价值全在最后半句：**让 12 刀各自可独立回滚**。拆分已完成（九个子系统抽出 + #166 的门族），过渡形态的价值随之用尽，剩下的 199 个转发体是纯粹的转发税：每一次读代码、每一次加方法、每一次 debug 都要穿过一层什么都不做的函数。

第二件必须纠正的事：**「公共面零改动」是逐刀纪律，不是不变量。** 这句话在本仓出现过四处，**每一处都限定在那一票的操作范围内**：ADR-0043 §理由、ADR-0044 §「不动公共面」（原文自带「**#152 已确立纪律**」字样）、ADR-0045 §46 与 §107、ADR-0048 §「公共面零改动」。而 ADR-0043 自己否决"解散门面"的理由写的是「**违反增量纪律（一刀动全部消费方）**」——那是"别一刀切完"，不是"永远不许"。把它读成不变量，会用一条工程纪律去否决掉它存在的理由。同一处 ADR-0043 还写了「门面的价值是公共面的稳定」——这里的"公共面"应读作**产品契约**（HTTP 路由路径与响应形状、agent 工具名与 JSON schema、磁盘文件格式），**不含引擎门面签名**。引擎门面签名是**内部接缝**，正是本 ADR 要重构的对象。附一条事实：**UI 从不经过门面**（它走 HTTP，`ui/src/api.ts` 的 139 处调用点是 HTTP 级的），从来不是门面的消费方。

第三件：**#169 把这一项的成本结构改了，而没有人回头重开它。** ADR-0043 写下"一刀动全部消费方"时，"全部"是约 **2000 行手写投递面代码**（`handleApi` 990 行 if 链 + 工具面 941 行），每一条都是手写 `engine.X(...)`。#169 之后生成路径是 `rt.engine[engine](...args)`（`src/host/api.ts`）——**一个字符串查表**。今天的"全部消费方"实测是：tests 直调 **1086 处 / 154 个方法 / 70 个测试文件**；host 例外 handler 直调 `rt.engine.X` **164 处 / 109 个方法**；注册表 **154 条** `engine` 字段；门面构造里的**接线箭头函数 108 条**（其中 **102** 条回引门面自身方法、**4** 条直指子系统、**2** 条取门面属性如 `jolRng`）。这些是机械改写，不是设计工作。

关键裁决：

- **终态形状 = C：hub 保留为纯容器，公开面改路径。** hub 继续喂子系统的接线、继续承载装配域方法（加载与解析／status/recommend／doctor/rebuild／生成任务持久化／私有 helper），但**不再暴露 199 个扁平转发方法**；消费方写 `engine.<子系统>.<方法>`。
- **R6 不变。** 子系统仍不 import `engine/index.ts`，跨子系统仍经 hub 的接线回引（`this.e.<方法>` 注入窄面）——hub 保留，正是为了让 R6 的形态继续成立。**只有被否决的选项 D 才需要放弃 R6。**
- **注册表的 `engine` 字段语义升级为「子系统 + 方法」**，gate ① 随之改断言子系统原型（今天它在 `tests/commands.test.ts:51` 用 `LearnhubEngine.prototype` 断言「引擎入口存在」）。这条门的价值不变——它仍是"接线指向不存在方法"的结构性拦截——只是断言面从门面原型搬到子系统原型。
- **产品契约不动清单（本 ADR 与 F1 唯一不可触碰的面）**：① HTTP 路由路径与响应形状（`tests/host-routes.test.ts` 的 464 条探针 + `host-routes-snapshot.json`）；② agent 工具名与 JSON schema（`tests/tools-face.test.ts` 的 259 条探针 + `host-tools-snapshot.json`）；③ 磁盘文件格式（vault 正典）；④ 既有测试的对外行为断言。**路由路径、工具名、响应形状逐字不变**——这是 ADR-0038／ADR-0045 的分流纪律与"不新增可达性"的落点。
- **为什么不是 B（运行时装配的扁平名字面）**：B 与 C 的收益**严格重合**——那 700 行转发层在两者下都消失；差别只在代价落在哪一侧。B 省下调用点改写，但代价是 hub 的方法**不再有真实声明**：`grep <方法名>` 找不到定义、IDE 不能跳转，且 gate ① 的权威要从类原型搬到一张装配表。而本仓库的门**全部是文本扫描**（`scripts/undefined-scan.mjs`／`scan-deps-face.mjs`／`scan-budget.mjs`／`scan-invariant.mjs`／`scan-types.mjs`／`arch-baseline.mjs`），`docs/agents/` 的整套导航纪律建立在"路径可推、符号可搜"上——**这条恰是 B 破坏的**。附实测记录，免得后来者以为 B 卡在门上：G1 的调用识别正则是 `(?<![\w.$])([a-zA-Z_]\w{2,})\s*\(`，**负向后顾把成员调用（`this.X(`／`rt.engine.X(`）全部排除**，所以删掉转发体**不会**触发 G1。B 的问题不是门会炸，是符号不可导航。
- **为什么不是 D（取消 hub、子系统互接）**：今天整个 `src/` 的**零环（R7）是靠星形拓扑达成的**——一切跨子系统调用经 hub。取消 hub 就是把星形换成网状，而 proposals／projects／graph／growth 之间本来就不是有向无环（`graphApply('enrich')` 一类旁路即是实证，见 ADR-0044 登记的第二处松动），**R7 会立刻开火**。D 的真正前置是**重划域边界**，那是另一个量级的工作，另开票。
- **时序：F1 排在 C2 与 B2 之后**（`blocked-by #179`、`#181`）。理由：C2 会按域搬移文件、B2 会搬移 `proposals.ts` 的方法归属，两者都会改变"某个方法属于哪个子系统"；F1 的核心工作正是"把每个调用点指到正确的子系统"，在这两票落地前做会批量返工。

边界：

- **本 ADR 只定终态，不施工**；施工票 #182 **立而不排期**。
- ADR-0043 的**分节对照表**（52 节 → 子系统的归属）**继续有效**，本 ADR 不改子系统划分、不改九个子系统的边界。
- ADR-0043 的**枢纽领主判定线**（领主文件 importer ≥5 个 engine 模块）与「零既有模块搬移、接缝路径不晃」原则**不变**。
- 门在 F1 施工期间**只作棘轮**（ADR-0047）；F1 若改文件归属，**规模与宽度阈值重推**，不是就地调。
- **不改 ADR-0038 的分流纪律**：本 ADR 不动任何命令的可达性（不新增工具、不改路由路径、不改 mode）。
- **不改 `ui/src/api.ts`**：它的 111 个端点函数名与签名、139 处调用点都不受本 ADR 影响（UI 走 HTTP）。
- ADR-0045 登记的"两处有理由的保留"（`/experiments` 复合响应 3 行手写；`ui/src/api.ts` 40 处内联响应类型）**不在本 ADR 处理**。
- **ADR-0013 的测试缝**（tests 直 import 引擎模块、`engine.store`）是文档化契约：本 ADR 改的是门面的公开面，`engine.store` 这条缝的处置**随 F1 单独裁并登记**——若保留，在 F1 票面写明理由。
- ADR-0042 的 R1–R7 与 ADR-0044 的四层责任表**均不改**：本 ADR 只改应用层内部 hub 的对外形状。
- `docs/adr/0043` 与 `docs/adr/0045` 已补交叉引用指向本 ADR（0043 注明「聚合+转发」是过渡形态；0045 注明其"另开票"的终极形态已由本 ADR 定案）。

替代方案（否决）：

- **保持现状 + 加一条"每个公共方法恰是一次转发"的门**（冻结过渡形态）——成本最低，也能把"接线指向不存在的方法"变成不可写。**否决理由：它没有实现"转发层消失或自动生成"中的任何一个。** ADR-0045 已把这件事列为终极形态；加门只是把 ADR-0043 的过渡手段永久化。若终态裁定后仍想保留转发层，说明终态本身没被想清楚——**门是执法手段，不是终态**。
- **B 运行时装配（委托表 / Proxy 生成扁平名）**——见关键裁决；收益与 C 重合而代价落在"符号可导航"这条本仓最看重的性质上。
- **D 取消 hub、子系统互接**——见关键裁决；前置是重划域边界。
- **代码生成转发方法（加构建步骤）**——ADR-0045 已否决同类（生成 `ui/src/api.ts`：「加 build 步骤是 ADR-0042 同类的工具链成本」，破零依赖口径）。门面侧同理；C 形态不需要任何构建步骤。
- **一次性改完全部 1086 + 164 处调用点**——违反 ADR-0043 的增量纪律（一刀动全部消费方，不可回滚）。F1 按子系统分批，分批顺序有现成依据：转发接收者分布 learner 41／content2 34／project 23／bank2 22／channels 18／lab 17／graph 15／growth2 15／sched2 11／registry 3。
