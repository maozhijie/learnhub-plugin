# 内容删除与生成任务注册表联动：悬空即清、无墓碑、保留期跨重启

生成任务注册表（`genJobs` + `state/生成任务.json`）的任务键只是入队时刻拼接的「课程/节点」字符串，与课程注册表和图之间没有外键：课程删除（`courseDelete`）与编辑批的 `del_node`/`rename` 都不触碰它，读取侧（`generate/status`）也不过滤，于是已删内容的任务记录永久滞留在面板上；又因终态保留期靠进程内 `setTimeout` 兜底、重启恢复块从不补挂，凡经历过一次重启的终态记录连 30 分钟/24 小时的保留期都失效（实证：失效后 3–7 天的 done/failed 记录仍在 status 里）。本次裁决清扫契约：**内容不在 ⟹ 注册表里没有它的任务**；终态保留期是注册表的契约而非进程的附属品。

关键裁决：
- **悬空任务记录唯一处置是清除，不做墓碑**。「引用已不存在课程/节点的任务记录」不是合法状态：失败讨论、重试、进度展示对已删内容没有任何消费方——标注「内容已删除」只留下零价值的考古行。
- **清扫以存在性判定为准，读侧不过滤**。存在性 = 注册表精确匹配（name/id，`get`-null 语义；停用课程不算缺失，内容仍在）＋图节点名集；课程级任务（种子/生长/富化/罗盘/反编译/计划/里程碑，node 槽是标签）只看课程。`generate/status` 原样吐注册表——status 如实反映账面，账面不干净是清扫的职责，不是视图过滤的职责（旧 `contentVersion` 的宽 catch 分不清「缺失」与「读失败」，不配当过滤依据）。
- **写侧联动是每条删除路径的义务**：`courseDelete`（HTTP 与 agent 工具两处）、提案统一 apply（`/proposals/apply` 与 `learnhub_graph_apply`）、生长批受理出口（教练批可含 del_node/rename）、复诊不达标自动剪除（无人审 del_node）之后都接同一把 `sweepGenJobs`。**未来新增任何删除/改名路径必须接同款清扫——这是不变量，不是可选优化。**在途悬空记录置取消旗标后出册（runner 持同一对象，下个检查点中止；落盘序列化取自 Map，已删条目的终态不会复活）。
- **保留期跨重启：时间戳结算，不靠定时器存活**。终态进入时盖 `finishedAt` 戳随注册表落盘（保留期起算点）；恢复时按时间戳清扫超期记录、幸存终态按剩余时长补挂定时器。旧档无戳回退 `startedAt`（只影响迁移首启，存量滞留记录恰是超期最久的，首启即清）。
- 恢复的排队记录悬空则弃、存活则维持「保留＋队列暂停」——不自动开跑的惊吓防护不变。

替代方案（否决）：
- **读侧过滤**（status 丢悬空记录）——单点收口、能拦住一切悬空来源，但 API 从此说谎：账面有而视图无，排查「记录去哪了」无从下手；且把「内容删除」这个事实从引擎状态搬进了展示层假设。
- **墓碑/「内容已删除」标注**——保留一行零消费方的展示负担，还要给注册表加状态位，违背清扫的最小性。
- **只做启动清扫**——最便宜，但运行期删除后记录要挂到下次重启才消失，删除的当下面板就是脏的。
